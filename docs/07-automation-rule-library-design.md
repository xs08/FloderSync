# 自动化规则库设计

状态：已实现（2026-09-03）

## 1. 目标

FloderSync 增加可复用的自动化规则库。用户可以先在“自动化”中创建规则，再让多个仓库引用同一条规则；仓库也可以不引用共享规则，直接保存自己的自动同步配置。

一条自动化规则定义完整的自动同步方案：

- 什么时候同步：新增 commit、固定间隔、每日指定时间。
- 如何整合远端更新：Rebase 或 Merge。
- 是否自动提交，以及提交者和提交信息模板。

仓库路径、远端名称、当前分支策略和仓库启用状态仍属于仓库本身，不进入共享规则。自动提交配置属于完整自动化方案，因此既可保存在仓库自定义配置中，也可进入共享规则。

## 2. 用户模型

每个仓库只能选择一种自动化配置来源：

| 来源 | 语义 |
| --- | --- |
| 使用共享规则 | 保存稳定的规则 ID。规则保存后，所有引用仓库从下一次触发开始使用新配置。 |
| 自定义配置 | 配置只属于当前仓库，不受规则库变化影响。 |

从共享规则切换为自定义配置时，以当前有效规则配置作为自定义配置的起点，避免切换瞬间改变行为。手动同步不依赖触发条件，仍使用当前有效的自动提交与远端整合配置。

## 3. 触发条件

规则和仓库自定义配置使用同一个编辑器。一套配置可以包含以下触发条件，同类型最多一项；共享规则至少启用一项，仓库自定义配置可以全部关闭以暂停自动触发而保留手动同步：

### 3.1 新增 commit

- 普通工作区文件变化不触发同步。
- 监听 `HEAD`、当前分支 ref 与 reflog 的元数据事件，去抖后比较当前 `HEAD` revision；只有 revision 变化才触发。
- 同步任务开始前暂停该仓库检测，完全空闲后读取最新 `HEAD` 作为基线再恢复，避免自动 commit、pull、rebase 或 merge 造成额外同步。
- 初次启用监听只建立 revision 基线，不立即触发。

### 3.2 固定间隔

- 每 5 分钟。
- 每 10 分钟。
- 每 1 小时。
- 自定义间隔。

自定义间隔限制为 1 分钟至 24 小时。下一次间隔从上一次同步完成后开始计算。

### 3.3 每日指定时间

每天可以设置一个或多个本地时间点。第一项新增为 `00:00`；后续新增取当前列表末项加一小时并追加到末尾，超过 `23:00` 时保持 `23:00`。编辑期间不自动排序或去重，避免调整某一项时改变其他行；保存规则时统一排序，若存在重复时间则拒绝保存并提示用户。系统时区或夏令时变化由 `Calendar` 计算处理。

## 4. 远端整合策略

| 策略 | Git 行为 | 产品语义 |
| --- | --- | --- |
| Rebase，默认 | `git pull --rebase <remote> <branch>` | 将尚未推送的本地提交应用到远端最新提交之后，保持历史线性。 |
| Merge | `git pull --no-rebase --no-edit <remote> <branch>` | 保留两侧历史；产生分叉时允许 Git 创建 merge commit。 |

用户只能选择受支持的策略，不能输入任意 Git 命令或附加参数。两种策略发生冲突时都停止后续 push，记录为“需要用户处理”，且不自动执行 `rebase --abort`、`merge --abort`、强制推送或破坏性恢复。

## 5. 数据模型

```text
AutomationRule
  id, name, configuration

AutomationConfiguration
  policies[], integrationStrategy, automaticCommit

AutomaticCommitConfiguration
  isEnabled, authorName?, authorEmail?, messageTemplate

SyncProfile
  repository fields,
  customAutomationConfiguration,
  automationRuleID?
```

`automationRuleID == nil` 表示使用仓库自定义配置；非空时由解析器查找共享规则并生成只用于运行时的有效配置。调度器和同步引擎只消费解析后的配置，不直接读取规则库。

规则名称去除首尾空白后必须非空，并在忽略大小写与变音符号后保持唯一。

## 6. 规则生命周期

- 新建规则：创建草稿，完成校验后保存。
- 编辑规则：如果已被仓库引用，保存按钮旁显示影响的仓库数量；保存为一次原子配置更新。
- 重命名规则：引用使用 UUID，不受名称变化影响。
- 删除未引用规则：确认后删除。
- 删除已引用规则：不能留下悬空引用。用户可以取消，或先把规则配置复制到每个引用仓库的自定义配置，再删除规则。
- 缺失引用：若配置损坏导致规则 ID 无法解析，跳过该仓库的自动调度并在设置中显示配置错误；手动同步仍可用。

规则保存或仓库来源变化后取消旧的等待任务并重新配置调度器。已经进入同步引擎的运行不中断；下一次触发使用最新配置。

## 7. 持久化与迁移

配置文件当前为 schema v4，根对象同时保存 `profiles` 与 `automationRules`。写入仍使用原子替换并保留最近备份。

schema v1 迁移规则：

- 每个仓库原有 `policies` 原样迁移为仓库自定义配置。
- 原有文件变化策略迁移为新增 commit 检测。
- 整合策略迁移为 Rebase。
- 不自动生成共享规则，避免在未经用户确认时关联多个仓库。
- 保留原提交信息模板，并默认开启自动提交以兼容既有行为。schema v2/v3 同样迁移为 v4；共享规则继承首个引用仓库的旧提交模板。

## 8. UI 信息架构

“自动化”页面使用主从结构：左侧规则列表及新增/删除操作，右侧为名称、触发条件、自动提交、远端整合策略和引用仓库列表。共享规则使用明确的保存操作，避免编辑过程中的半成品配置立即影响多个仓库。

仓库详情增加“自动同步”区域：

- 配置来源：共享规则或自定义配置。
- 共享规则：规则选择器、有效配置摘要和“前往编辑规则”。
- 自定义配置：展示与规则页一致的触发条件、自动提交和整合策略编辑器。

界面沿用原生 macOS `Form`、`Picker`、`DatePicker` 和主从列表，不新增非标准控件或装饰性动效。状态不能只依赖颜色。

## 9. 历史与可解释性

每次自动运行保存触发来源和整合策略快照，例如：

- `新增 Commit · Rule 1 · Rebase`
- `定时同步 · 仓库自定义 · Merge`

规则后续被重命名或修改时，既有历史仍保留运行当时的信息。

## 10. 验收条件

- 两个仓库引用同一规则时，保存规则变更会同时重配两个仓库。
- 自定义仓库不受共享规则修改影响。
- 从共享规则切换到自定义配置不会立即改变有效行为。
- 普通文件变化不触发；新增 commit 会触发；同步任务自身造成的 revision 变化不会重触发。
- 固定间隔和每日多个时间点正确调度，且不会保留重复任务。
- 每日新增从 `00:00` 开始逐小时递增并封顶 `23:00`；编辑期间顺序稳定，保存时排序，重复时间无法保存。
- Rebase 与 Merge 分别执行明确、非交互的 Git 参数。
- 任一整合策略出现冲突后都不会执行 push。
- 删除规则不会留下悬空引用。
- schema v1/v2/v3 配置迁移为 schema v4，并保留原提交模板、自定义配置和 Rebase；旧文件变化策略迁移为新增 commit 检测，旧共享规则按首个引用仓库的模板建立自动提交配置。
